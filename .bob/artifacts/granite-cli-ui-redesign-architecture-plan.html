1. The core idea: one entry point, two rendering modes

The decision happens in main(), at the match cli.command branch. The None arm (no args) currently prints a static help block. That becomes the interactive TUI entry point. Every Some(…) arm that runs a command routes through a single Output object that knows which mode it's in.

InvocationModeWhat happens
granite-cli (no args) Interactive TUI Enter a full ratatui application — navigation panel on the left, content pane on the right. User presses keys to browse models, providers, capabilities.
granite-cli model catalog Formatted output Run the command, render the result as a styled ratatui table written to stdout once (no event loop), then exit. Pipeable, scriptable.
granite-cli provider setup … Interactive wizard Setup wizards stay as dialoguer-based prompts for now (they're already interactive line-by-line). Eventually these migrate to ratatui forms.
Key insight: "formatted output" doesn't mean a live event loop. For non-interactive commands ratatui still renders to stdout, it just does one draw pass and exits. This gives you coloured tables, borders, and alignment without trapping the user in a UI they need to quit.

2. The central abstraction: the Output trait

This is the core of the whole design. Instead of every command calling println! directly, commands call methods on an &dyn Output they receive as an argument. The two concrete implementations are PlainOutput (one-shot ratatui render) and the interactive TUI handles itself.

Think of it like Java's PrintStream — System.out.println() vs writing to a file. You swap the stream, not the code that uses it.

// src/utils/ui/output.rs  ← THE key new file

pub trait Output {
    /// Render a flat table: headers + rows
    fn table(&self, title: &str, headers: &[&str], rows: &[Vec]);

    /// Render a key→value detail block  
    fn detail(&self, title: &str, fields: &[(&str, String)]);

    /// Render a status row (used for health checks etc.)
    fn status(&self, label: &str, ok: bool, detail: &str);

    /// Print a plain informational message
    fn info(&self, msg: &str);

    /// Print a warning (yellow)
    fn warn(&self, msg: &str);

    /// Print an error (red)
    fn error(&self, msg: &str);
}

// ── Two concrete implementations ──────────────────────────────

/// One-shot: renders to stdout using ratatui, then returns.
/// Used when args were given (non-interactive mode).
pub struct TerminalOutput;
impl Output for TerminalOutput { ... }

/// No-op / passthrough for the interactive TUI —
/// the TUI owns its own render loop, commands just update shared state.
pub struct TuiOutput { ... }
impl Output for TuiOutput { ... }

How a command uses it — before and after

// BEFORE (src/commands/provider.rs) — hardcoded println!
pub fn catalog(_ctx: &AppContext) -> Result<()> {
    let providers = PROVIDER_REGISTRY.entries();
    println!("{:<20} {:<10} {:<35}", "ID", "TYPE", "ENDPOINT");
    println!("{:<20} {:<10} {:<35}", "----", "----", "--------");
    for (id, p) in &providers {
        println!("{:<20} {:<10} {:<35}", id, p.provider_type, p.default_endpoint);
    }
    println!("Total: {} providers", providers.len());
    Ok(())
}

// AFTER — output-agnostic
pub fn catalog(_ctx: &AppContext, out: &dyn Output) -> Result<()> {
    let providers = PROVIDER_REGISTRY.entries();
    let rows: Vec> = providers.iter()
        .map(|(id, p)| vec![id.to_string(), p.provider_type.to_string(), p.default_endpoint.clone()])
        .collect();
    out.table("Provider Catalog", &["ID", "TYPE", "ENDPOINT"], &rows);
    Ok(())
}

The command doesn't know or care whether it's running in TUI mode, piped to a file, or printing to a terminal. That decision lives entirely in whichever Output implementation was passed in.

The rename is backward-compatible. src/utils/mod.rs currently does pub use schema_prompt::prompt_from_schema. After the move it does pub use ui::prompt::prompt_from_schema. Every existing caller in commands/provider.rs sees the same import path — zero changes needed there.

4. How main.rs changes

// src/main.rs — the two paths diverge here

async fn main() {
    let cli = Cli::parse();

    let result = match cli.command {

        // ── No args → full interactive TUI ───────────────────────────
        None => {
            let ctx = AppContext::new()...;
            utils::ui::run_interactive_tui(ctx).await
            //         ^^^^^^^^^^^^^^^^^^^
            //         new function in src/utils/ui/app.rs
            //         owns the terminal until user exits
        }

        // ── Args given → formatted output mode ───────────────────────
        Some(cmd) => {
            let out = utils::ui::TerminalOutput::new();
            //        ^^^^^^^^^^^^^^^^^^^^^^^^^^
            //        the one-shot ratatui renderer
            let mut ctx = AppContext::new()...;
            dispatch_command(&mut ctx, cmd, &out).await
        }
    };
    ...
}

5. How commands change (the migration contract)

Every public method on ModelCommands, ProviderCommands, CapabilityCommands gets one extra parameter appended: out: &dyn Output. All println! calls become out.table(…) / out.info(…) / out.status(…). That's the entire change per command.

Old callNew call
println!("{} rows", n)out.info(&format!("{} rows", n))
column-aligned println! loopout.table("Title", headers, rows)
eprintln!("Error: {}", e)out.error(&format!("{}", e))
println!("Name: {}", v) blockout.detail("Title", &[("Name", v), …])
health latency rowout.status(id, healthy, error_msg)
Don't change setup/wizard commands yet. model setup and provider setup mix println! with dialoguer prompts interleaved. Those are a separate migration effort and work fine today. Touch them only after the read-only commands are fully migrated.

6. Phased implementation plan

1
Scaffold the ui module, move schema_prompt
No behaviour change · ~30 min
  1. Create src/utils/ui/mod.rs and src/utils/ui/prompt.rs
  2. Move the contents of schema_prompt.rs into prompt.rs verbatim
  3. Delete schema_prompt.rs
  4. Update src/utils/mod.rs: pub mod ui; pub use ui::prompt::prompt_from_schema;
  5. Run cargo test — should pass, nothing changed externally
2
Define the Output trait + TerminalOutput (plain version)
Core abstraction · ~2 hrs

Create src/utils/ui/output.rs with the Output trait and a TerminalOutput that just calls println! internally for now. This lets you migrate the command layer before the ratatui rendering is done — the trait is stable, the implementation can improve later.

// Phase 2: TerminalOutput is basically a pretty println! wrapper
impl Output for TerminalOutput {
    fn table(&self, title: &str, headers: &[&str], rows: &[Vec<String>]) {
        println!("\n{}", title);
        // existing column-format logic goes here
    }
    fn info(&self, msg: &str)  { println!("{}", msg); }
    fn warn(&self, msg: &str)  { println!("Warning: {}", msg); }
    fn error(&self, msg: &str) { eprintln!("Error: {}", msg); }
    ...
}

Thread out: &dyn Output through main.rs and all command methods. Every println! in the read-only commands (catalog, list, info, health) becomes an out.* call. Compile and test.

3
Upgrade TerminalOutput to real ratatui rendering
Visible improvement · ~1 day

Now that all commands talk to the Output trait, you can swap the internals of TerminalOutput to use ratatui widgets. The command files don't change at all — only output.rs changes.

Create src/utils/ui/tui.rs with a helper:

/// One-shot render: draw `widget` to the terminal, then return.
/// No event loop — just draw and exit.
pub fn render_once(widget: impl Widget) -> anyhow::Result<()> {
    let mut terminal = setup_terminal()?;
    terminal.draw(|frame| frame.render_widget(widget, frame.area()))?;
    restore_terminal(terminal)?;
    Ok(())
}

Implement TerminalOutput::table() using ratatui's Table widget through render_once. The table gets borders, column alignment, and colour for free.

4
Build the interactive TUI home screen (None arm)
New feature · ~1–2 days

Create src/utils/ui/app.rs. This owns the full ratatui event loop. The UI has two panels: a left navigation list and a right content pane. The content pane renders the exact same data that the commands render, but now navigable.

pub struct App {
    pub ctx: AppContext,
    pub selected_section: Section,  // Models / Providers / Capabilities
    pub selected_item: usize,       // row index in the list
    pub mode: AppMode,              // Browse | Detail | Setup
}

pub async fn run_interactive_tui(ctx: AppContext) -> anyhow::Result<()> {
    let mut terminal = setup_terminal()?;
    let mut app = App::new(ctx);
    loop {
        terminal.draw(|frame| app.render(frame))?;
        if let Event::Key(key) = event::read()? {
            match app.handle_key(key) {
                Action::Quit => break,
                Action::Continue => {}
            }
        }
    }
    restore_terminal(terminal)?;
    Ok(())
}

The app.render(frame) method reuses the same ratatui table widgets from Phase 3 — no duplicated logic.

5
Migrate setup wizards to ratatui forms (optional, later)
Large effort · future

Replace dialoguer Input / Select / Confirm in prompt.rs with a ratatui form widget. This is the hardest step because ratatui raw mode conflicts with dialoguer's line-reading. Don't do this until Phases 1–4 are solid. Dialoguer works fine and the prompt.rs module boundary means you can swap it independently later.

8. What stays in dialoguer — don't touch yet

src/utils/ui/prompt.rs (the renamed schema_prompt.rs) keeps using dialoguer exactly as-is. The module boundary is the decoupling point — it's internally dialoguer-based, but callers only see prompt_from_schema(schema, defaults). When you're ready to ratatui-ify it, you rewrite the internals without changing any call site.

Same for the inline Confirm / Select calls in the setup command bodies — leave those for Phase 5.
