1. The Factory Pattern — Concept First

The Factory Pattern is an OOP idea where instead of writing let x = MyThing::new() directly, you go through a middleman — the factory — that decides which concrete type to create based on a name or key you give it at runtime.

Why would you want that? Because your code only knows about the abstract interface (a trait in Rust, an interface/abstract class elsewhere), not the specific concrete implementation. This means you can add new implementations without touching the code that uses them.

// Without a factory — caller must know the concrete type:
let provider = OpenAIProvider::new(config);

// With a factory — caller only knows the string name:
let provider = PROVIDER_REGISTRY.construct("openai-compatible", config);
// Returns Box<dyn Provider> — caller never sees the concrete type at all

In OOP terms, the factory owns a registry (a map of name → constructor function). Registering and constructing are separate steps. This is also sometimes called a plugin registry or service locator.

The three-trait contract used here

Every concrete type that wants to live in a factory must implement three things:

Thing to implementWhat it does
ConfigConstructable Provides a new(cfg: &serde_json::Value) constructor. The factory uses this to build instances.
The domain trait (Provider, Model, or Capability) The actual behavioural API the rest of the code uses. The factory returns Box<dyn Provider>, so callers stay decoupled from the concrete type.
Has<Trait>Metadata (generated by the macro) Supplies static description info (name, type, schema, defaults) so the factory can answer questions about a type without constructing an instance.

2. How It's Built in Rust: the define_factory! macro

The entire factory machinery is generated by a single macro call in each domain's base.rs:

// src/models/base.rs  (last two lines)
use crate::define_factory;
define_factory!(Model, ModelMetadata, ModelFactory);

// src/providers/base.rs
define_factory!(Provider, ProviderMetadata, ProviderFactory);

// src/capabilities/base.rs
define_factory!(Capability, CapabilityMetadata, CapabilityFactory);

That one macro expands to roughly:

// 1. A "type-erased" internal trait for each entry in the HashMap
//    (this is the key trick — you can't store Box<T> for different T
//     in the same Vec, but you CAN store Box<dyn SomeTrait>)
trait ModelMetadata_: Send + Sync {
    fn describe(&self) -> ModelMetadata;       // return metadata without an instance
    fn construct(&self, cfg: &Value) -> Box<dyn Model>; // build an instance
    fn config_schema(&self) -> schemars::Schema;
    fn default_config(&self) -> Value;
}

// 2. A zero-size "phantom" wrapper that implements ModelMetadata_ for each T
struct MetaOf<T>(PhantomData<T>);
impl<T: Model + HasModelMetadata> ModelMetadata_ for MetaOf<T> {
    fn describe(&self) -> ModelMetadata { T::metadata() }
    fn construct(&self, cfg: &Value) -> Box<dyn Model> { Box::new(T::new(cfg)) }
    ...
}

// 3. The actual factory struct — just a HashMap
pub struct ModelFactory {
    registry: HashMap<&'static str, Box<dyn ModelMetadata_>>,
}
impl ModelFactory {
    pub fn register<T>(&mut self, name: &'static str) { ... }
    pub fn construct(&self, name: &str, cfg: &Value) -> Result<Box<dyn Model>, String> { ... }
    pub fn get(&self, name: &str) -> Option<ModelMetadata> { ... }
    pub fn entries(&self) -> HashMap<&str, ModelMetadata> { ... }
}
PhantomData<T> is a Rust idiom for "I'm logically associated with type T but I don't actually store any T values". It's zero bytes at runtime — it's purely a compile-time marker so the type system stays happy. That's how one empty struct like MetaOf<OpenAIProvider> can implement "construct an OpenAIProvider" without holding an actual instance.

Where the static registries live

Each domain's mod.rs creates a static (a global, lazily-initialised singleton) and populates it at startup:

// src/models/mod.rs  (conceptual)
pub static MODEL_REGISTRY: Lazy<ModelFactory> = Lazy::new(|| {
    let mut f = ModelFactory::new();
    f.register::<GraniteTextModel>("granite-3.3-8b-instruct");
    f.register::<GraniteVisionModel>("granite-vision-3.3-2b");
    // ...
    f
});

Commands like ModelCommands::catalog() then just call MODEL_REGISTRY.entries() to list everything, or MODEL_REGISTRY.get("granite-3.3-8b-instruct") to look up one.

3. The Full CLI Flow — Request to Output

User types command → main() via clap → run_*_command() → *Commands::method() → REGISTRY.get/construct → println! / dialoguer
StepFileWhat happens
1. Parse src/main.rs Cli::parse() — clap reads argv and fills the Commands enum. The enum variants directly mirror the CLI grammar (granite-cli model catalog → Commands::Model(ModelSubcommands::Catalog { .. })).
2. Route src/main.rs A big match cli.command sends each variant to a run_*_command() async function. AppContext (which just holds the loaded config) is created here and passed down.
3. Dispatch src/commands/model.rs etc. The run_*_command() functions do a second match on subcommands and call ModelCommands::catalog(ctx, filter), ModelCommands::info(ctx, id), etc. These are plain static methods on unit structs (no state).
4. Registry query src/models/mod.rs etc. Command methods call into the static registry (MODEL_REGISTRY.entries(), PROVIDER_REGISTRY.construct()) to get metadata or build objects.
5. Config read/write src/config/mod.rs For list and setup commands, ctx.config (loaded from ~/.granite/config.yaml) is read or mutated and saved back.
6. Output everywhere Directly println! to stdout. For interactive setup flows, dialoguer widgets (Select, Input, Confirm, Password) are used.
AppContext is a thin wrapper around Config. It exists so future phases can add more app-level state (e.g. caches, sessions) without changing every function signature. For now it's essentially just config: Config.

4. Output Audit: who prints what?

Almost all output is done with raw println! / eprintln!. There is no output abstraction layer. Here is the complete inventory:

FileMechanismWhat
src/main.rs println! / eprintln! The no-command help block; error reporting in the None arm
src/commands/model.rs println! Catalog table, list table, info detail block, setup prompts/messages
src/commands/capability.rs println! Catalog table, list table, info block, setup messages
src/commands/provider.rs println! + print! Catalog/list/health tables; setup wizard messages; print! used once for inline comma-separated auth list
src/utils/schema_prompt.rs dialoguer widgets + println! Interactive field-by-field config prompts (Input, Password, Confirm, Select). One println! for object section headers.
src/utils/web_fetch.rs none No output — pure data transformation (fetch → markdown).
There is no central print/format helper. Every call site owns its own formatting strings. This is what makes ratatui attractive — you'd replace these scattered println! sites with a single rendering layer.

5. Removing web_fetch — Blast Radius

Verdict: Blast radius is zero. Safe to remove with no functional changes anywhere.

Here is the complete dependency graph for src/utils/web_fetch.rs:

src/utils/web_fetch.rs
  └─ defines: fetch_markdown(), extract_urls()
       └─ re-exported by: src/utils/mod.rs (pub use web_fetch::{...})
            └─ consumed by: NOTHING — grep across all *.rs finds zero call sites

The two functions are exported but never called by any other Rust code in the project. The only references outside the file itself are the re-export line in src/utils/mod.rs and the file's own internal tests.

What to delete

  1. src/utils/web_fetch.rs — the whole file
  2. In src/utils/mod.rs: remove lines pub mod web_fetch; and pub use web_fetch::{fetch_markdown, extract_urls};
  3. In Cargo.toml: remove reqwest, html2md, and regex (all three are only used here — verify regex isn't used elsewhere first; it appears only in web_fetch.rs)
Double-check regex before removing it from Cargo.toml — run grep -r "regex::" src/. The grep above only shows it in web_fetch.rs, but confirm before removing. reqwest and html2md are safe to drop.

6. Adding ratatui — Where, Why, and How

ratatui is already in Cargo.toml (ratatui = "0.30.2") so the dependency is there. What it does is give you a terminal UI framework: you describe what to draw (widgets like tables, paragraphs, lists, borders) and ratatui redraws the terminal on each frame using a double-buffering diff so only changed cells are written. It's not a "fire and forget println" — it owns the terminal for as long as the TUI is running.

Two modes of ratatui use — choose the right one

ModeWhen to useExamples
Full interactive TUI When the user will stay in a screen for a while and navigate around — e.g. a browsable model catalog List widget with scroll, modal detail panels, a setup wizard with live validation
One-shot pretty output When you just want nicer tables and formatting for a single command's output before returning control Coloured tables for catalog, list, health

For one-shot pretty output the right move is not ratatui — it's crossterm (which ratatui already depends on) for ANSI colours, plus something like the comfy-table crate for tables, or just manual ANSI escape strings. Ratatui's event loop overhead is overkill if you're not staying in the UI.

For a full interactive TUI experience (a real revamp), ratatui makes sense and here's where to put it:

Proposed file layout

src/
  utils/
    ui/
      mod.rs          ← replaces schema_prompt.rs as the "output home"
      tui.rs          ← ratatui Terminal setup/teardown, main event loop
      widgets/
        table.rs      ← reusable catalog/list Table widget
        detail.rs     ← model/provider/capability detail panel
        prompt.rs     ← setup wizard (wraps / replaces schema_prompt logic)
      theme.rs        ← colours, styles, shared visual constants

The ratatui event loop pattern

// tui.rs — skeleton
use ratatui::prelude::*;
use crossterm::event::{self, Event, KeyCode};

pub fn run_tui<S: AppState>(mut state: S) -> anyhow::Result<()> {
    // 1. Take over the terminal
    crossterm::terminal::enable_raw_mode()?;
    let mut terminal = Terminal::new(CrosstermBackend::new(std::io::stdout()))?;
    terminal.clear()?;

    loop {
        // 2. Draw from state
        terminal.draw(|frame| state.render(frame))?;

        // 3. Handle input
        if let Event::Key(key) = event::read()? {
            match key.code {
                KeyCode::Char('q') | KeyCode::Esc => break,
                _ => state.handle_key(key),
            }
        }
    }

    // 4. Restore the terminal
    crossterm::terminal::disable_raw_mode()?;
    Ok(())
}

Concrete migration path

Current commandratatui replacementEffort

Don't replace dialoguer with ratatui for the setup wizard yet. ratatui handles display, not input validation. You'd be rewriting schema_prompt.rs from scratch. The catalog/list/info/health read-only screens are the right starting point.

7. Renames & Refactors: schema_prompt → ui

Your instinct to make schema_prompt.rs the "main output home" and give it a better name is sound. Here's a concrete proposal:

Rename schema_prompt → ui as a module

// src/utils/ui/mod.rs
pub mod prompt;    // ← schema_prompt.rs moves here, renamed
pub mod render;    // ← new: all the println! table formatters move here
pub mod tui;       // ← new: ratatui integration when you're ready

pub use prompt::prompt_from_schema;
pub use render::{print_table, print_detail, print_status};

What render.rs looks like (the "pretty println" layer)

// src/utils/ui/render.rs
use crate::models::ModelMetadata;

pub fn print_model_catalog(models: &[(&str, &ModelMetadata)]) {
    // All the column-formatting logic from ModelCommands::catalog()
    // centralised here instead of in the command handler
}

pub fn print_model_detail(id: &str, model: &ModelMetadata) {
    // All the println! block from ModelCommands::info()
}

This gets you two real wins before you even touch ratatui:

  1. Commands become thin — they just call print_model_catalog(&models); no formatting logic in the command layer.
  2. Easy ratatui migration later — swap out print_model_catalog()'s body for a ratatui TUI call; zero changes to command files.

Recommended order of operations

  1. Remove web_fetch (zero risk, immediate cleanup)
  2. Create src/utils/ui/ module, move schema_prompt.rs → src/utils/ui/prompt.rs
  3. Extract all println! formatting from command files into src/utils/ui/render.rs
  4. Add a tui.rs stub and port the read-only catalog screens to ratatui one at a time
  5. Eventually replace the dialoguer wizard in prompt.rs with a ratatui multi-step form
