granite-cli — Architecture & Terminal Flow

How the pieces fit together — for someone new to Rust

1. The Coupled Parts at a Glance

The project has five distinct layers that each talk to the layer below. Understanding this stack is the key to navigating any file in the codebase.

Terminal / CLI layersrc/main.rs — clap parses argv into typed structs, routes to a command handler
↓ calls
Command layersrc/commands/{model,provider,capability}.rs — interactive wizards, output formatting with println!
↓ reads from
Registry layerMODEL_REGISTRY, PROVIDER_REGISTRY, CAPABILITY_REGISTRY — static catalogs of what exists
↓ resolves against
Dependency layersrc/dependency/mod.rs + src/providers/mod.rs::ProviderSource — matches what's needed to what's available
↓ persists to/from
Config layersrc/config/mod.rs — YAML files in ~/.config/granite-cli/ — the user's saved choices

2. How a Terminal Command Actually Works

Take granite-cli model setup granite-3.1-8b-instruct as a concrete walkthrough:

Step 1 — clap parses the arguments (main.rs)

// The #[derive(Parser)] macro generates this automatically.
// After Cli::parse(), the struct is fully populated:
Cli {
    command: Some(Commands::Model(
        ModelSubcommands::Setup {
            model_id: "granite-3.1-8b-instruct"
        }
    ))
}

No parsing code is written by hand. The structs are the CLI definition. clap generates help text, error messages, and type coercion from the struct annotations.

Step 2 — main() routes to the right handler

match cli.command {
    Some(Commands::Model(subcmd)) => {
        let mut ctx = AppContext::new()?;  // loads config from disk
        run_model_command(&mut ctx, subcmd).await
    }
    ...
}

AppContext is just a wrapper around Config — it's the user's saved state (which models they've configured, which providers, etc.). It's passed into every command handler.

Step 3 — the command handler runs (commands/model.rs)

pub async fn setup(ctx: &mut AppContext, model_id: &str) -> Result<()> {
    // 1. Look up model in the static registry
    let model = MODEL_REGISTRY.get(model_id)?;

    // 2. dialoguer prompts — Select shows a numbered list the user
    //    navigates with arrow keys and confirms with Enter
    let variant_index = dialoguer::Select::new()
        .with_prompt("Select model variant:")
        .items(&variant_options)
        .interact()?;  // ← blocks here waiting for user input

    // 3. dependency resolver — finds providers that can run this variant
    let requirement = VariantRequirement { format, precision };
    let source = ProviderSource::from_config(&ctx.config);
    let resolution = dependency::resolve(&requirement, &source);

    // 4. more dialoguer prompts to pick/configure a provider

    // 5. save to config
    ctx.config.insert_model(model_id, model_config);
}

Step 4 — dialoguer handles all terminal interaction

The project uses the dialoguer crate for every interactive prompt. There are three types used:

Dialoguer typeWhat it showsUsed for
dialoguer::SelectNumbered list, arrow key navigationPick a variant, pick a provider
dialoguer::InputText field with optional defaultEnter a URL, name an instance
dialoguer::ConfirmY/N promptOverwrite existing config?
dialoguer::PasswordMasked text inputAPI keys (via Secret schema marker)
Every .interact()? call blocks — it gives control to the terminal and waits for the user to press Enter. The ? propagates any error up to main().

Step 5 — schema-driven config prompt (utils/schema_prompt.rs)

For providers, the prompt wizard is completely generic. Instead of hardcoding "ask for base_url, then ask for api_key", it reads the JSON schema of the provider's config struct and generates prompts for every field automatically:

// In provider setup:
let schema = PROVIDER_REGISTRY.config_schema("openai-compatible");
let defaults = PROVIDER_REGISTRY.default_config("openai-compatible");
let config = prompt_from_schema(&schema, &defaults)?;
// Walks the schema, shows an Input for each string field,
// Password for fields marked "format: password" (Secret type),
// Confirm for booleans, etc.

This means adding a new field to OpenAIProviderConfig automatically adds it to the setup wizard — no wizard code to update.

3. The Registry Layer — catalog vs configured

After the upstream merge, every resource type has two distinct views. This is the most important conceptual split in the project:

catalog / REGISTRY (static, compile-time)

  • Built from resources/models.yaml via build.rs
  • Registered in the LazyLock statics at startup
  • Represents what could exist — what granite-cli ships with
  • Commands: model catalog, provider catalog, capability catalog
  • Never changes without a recompile

list / Config (dynamic, user-configured)

  • Loaded from ~/.config/granite-cli/ YAML at startup
  • Represents what the user has set up — their actual instances
  • Commands: model list, provider list, capability list
  • Changes every time the user runs a setup command
  • Multiple instances of one catalog type are allowed (e.g. two openai-compatible providers with different URLs)

4. The Dependency Layer — how model→provider matching works

When you run model setup and pick a GGUF/Q4_K_M variant, the CLI needs to find a provider that can actually serve it. This is handled by src/dependency/mod.rs:

// 1. Express what the model variant needs as a Requirement
let requirement = VariantRequirement {
    format: "GGUF",
    precision: "Q4_K_M",
};

// 2. Build a view of all configured + catalog providers
let source = ProviderSource::from_config(&ctx.config);

// 3. Resolve — pure logic, no I/O
let resolution = dependency::resolve(&requirement, &source);
// resolution.existing_instances = ["my-ollama"]   ← already configured, matches
// resolution.configurable_types = ["openai-compatible"] ← in catalog, could match

The resolver works in two passes for each dependency:

PassWhat it checksHow
Instance-levelAlready-configured live instancesadmits_instance(&dyn Provider) — asks the real object
Type-levelCatalog entries (not yet configured)admits_type(&ProviderMetadata) — checks metadata only

The command layer then turns a Resolution into user interaction: show existing matches as choices, offer "configure a new one" backed by the catalog types.

5. The Config Layer — how state persists

Every setup command ends by calling something like:

ctx.config.insert_model(model_id, model_config);
// This immediately writes to ~/.config/granite-cli/models/<id>.yaml

The config directory layout after a user has set up one model and one provider:

~/.config/granite-cli/
├── config.yaml                       # routing + shell settings
├── models/
│   └── granite-3.1-8b-instruct.yaml  # ModelConfig { provider_id, variant, enabled }
├── providers/
│   └── my-ollama.yaml                # ProviderConfig { provider_type: "openai-compatible",
│                                     #                  config: { base_url, api_key } }
├── capabilities/                     # empty until capabilities are registered
└── tools/                            # empty until Phase 3
The ProviderConfig.config field is a raw serde_json::Value — it's whatever the schema-driven prompt collected. This is how the same ProviderConfig struct can hold configuration for any provider type without knowing the provider's concrete struct at compile time.

6. The ModelFunction concept (new in this merge)

The upstream merge added ModelFunction as the vocabulary that connects models to providers. Instead of matching on API surface names directly, the system now asks: "what can this model do?" and "what does this provider serve?"
